# Scanmatik CAN/J1939 логгер

## О проекте

Практический **реверс-инжиниринг диагностического протокола автомобильного
блока APM (Volvo)** поверх CAN-шины — с нуля, без фирменного ПО Volvo, только
через J2534-адаптер (Scanmatik SM2/SM3) и самостоятельно написанные
мост/декодер:

- разобран и реализован диагностический обмен **UDS (ISO 14229)** — чтение
  идентов (VIN, номера ПО/железа), чтение и очистка кодов ошибок (DTC);
- расшифровка сырых кодов ошибок в человекочитаемый вид, в т.ч. по
  Volvo-специфичному справочнику (типы неисправностей, статус
  активна/неактивна);
- пассивный мониторинг **всего** трафика шины (не только диагностического
  обмена) с адресацией по **SAE J1939** и записью в CSV;
- опрос DTC сразу у всех адресов (ЭБУ), видимых на шине, а не только у
  одного заранее известного;
- разобраны и исправлены несколько независимых причин потери/повреждения
  кадров при плотном трафике на шине (подробности — в разделе ниже).

Дальше — техническое описание самой программы.

Мини-программа для логирования CAN-линии через прибор **Scanmatik** (SM2/SM3),
подключённый по USB. Отдельные кнопки **Подключиться** (живой просмотр шины)
и **Запись** (пишет в CSV, не разрывая соединение), переключатель режима шины
**CAN (обычный J2534)** / **SAE J1939**, выбор скорости.

## Готовый exe

Собран через PyInstaller в `dist\ScanmatikLogger\ScanmatikLogger.exe` —
просто запускайте его, Python на машине для этого не нужен (32-битный мост
`smbridge.exe` уже лежит рядом, в `dist\ScanmatikLogger\bridge\publish\`).

Чтобы пересобрать exe после изменений в `can_logger_gui.py`:

```powershell
py -m pip install --upgrade pyinstaller
py -m PyInstaller --noconfirm --onedir --windowed --name ScanmatikLogger can_logger_gui.py
# мост в exe-сборку сам не попадёт — скопировать вручную:
Copy-Item -Recurse -Force bridge\publish dist\ScanmatikLogger\bridge\publish
```

Вся папка `dist\ScanmatikLogger\` — самодостаточная, её можно целиком
скопировать на другой компьютер (Windows, тех же или более новых версий).

## Как это устроено

Драйвер Scanmatik — это стандартный **J2534 PassThru** DLL:

- `C:\Program Files (x86)\Scanmatik\smj2534.dll` — SM2 USB
- `C:\Program Files (x86)\Scanmatik\smj2534_0404_usb_sm3.dll` — SM3 USB

Обе DLL **32-битные** (зарегистрированы в `HKLM\SOFTWARE\WOW6432Node\PassThruSupport.04.04`).
На вашей машине установлен только 64-битный Python, а 64-битный процесс
физически не может загрузить 32-битную DLL через `ctypes`. Поэтому программа
состоит из двух частей:

1. **`bridge\`** — маленький 32-битный мост на .NET (`smbridge.exe`), который
   напрямую вызывает функции J2534 (`PassThruOpen/Connect/StartMsgFilter/ReadMsgs/...`)
   и печатает принятые кадры в stdout построчно.
2. **`can_logger_gui.py`** — обычное окно на Tkinter (Старт/Стоп, выбор
   устройства/режима/скорости, CSV-лог, live-просмотр). Само по себе битности
   не имеет значения — GUI просто запускает `smbridge.exe` подпроцессом и
   общается с ним через stdin/stdout.

Логгер (`can_logger_gui.py`) **только слушает шину** — только записывает
трафик, сам ничего не отправляет. Мост при этом умеет и слушать, и
отправлять кадры (`PassThruWriteMsgs`) — этим пользуется вторая программа,
`can_dtc_reader_gui.py` (см. ниже), которая сама опрашивает ЭБУ по UDS.

## Режим J1939

У прибора Scanmatik нет отдельного публичного заголовочного файла J2534 с
протокол-ID для J1939 (только .chm-справка и DLL), поэтому режим J1939
реализован **по общепринятой практике J2534-адаптеров для тяжёлой техники**
(так работают, например, интерфейсы NEXIQ USB-Link и Cummins USB-Link,
которые тоже есть в списке J2534-устройств на вашем компьютере):

- протокол подключения — обычный `CAN` (ID = 5),
- но с флагом **29-битного расширенного ID** (`CAN_29BIT_ID`, т.к. J1939
  всегда использует 29-битные идентификаторы),
- скорость — 250000 или 500000 бод (стандартные для J1939).

Если после сборки J1939-режим не подключается, а обычный CAN — подключается,
велика вероятность, что в `smj2534*.dll` для J1939 зарезервирован отдельный
Protocol ID. Тогда стоит:

1. Открыть `C:\Program Files (x86)\Scanmatik\scanmatik.chm` (можно через
   `hh.exe scanmatik.chm` или просто двойным кликом) и поискать "J1939" /
   "Protocol ID".
2. Или запустить `sm2ptconfig.exe` из той же папки — это штатная
   J2534-утилита Scanmatik, там тоже иногда виден список поддерживаемых
   протоколов.
3. Поменять константу протокола в `bridge/Program.cs` (переменная
   `protocolId`, сейчас всегда `J2534Const.CAN`) на найденное значение для
   режима `J1939` и пересобрать (`build_bridge.ps1`).

## Установка / сборка

Нужен **.NET SDK** (у вас уже есть — можно проверить `dotnet --version`).
Python не нужен для самого моста, но нужен для GUI (обычный `python`/`py`,
Tkinter входит в стандартную поставку).

1. Собрать мост:

   ```powershell
   powershell -ExecutionPolicy Bypass -File build_bridge.ps1
   ```

   Появится `bridge\publish\smbridge.exe`.

2. Запустить GUI:

   ```powershell
   py can_logger_gui.py
   ```

   (или дважды кликнуть на .py, если файлы Python ассоциированы с `py.exe`).

## Использование

1. В списке "Устройство J2534" выбрать нужный адаптер — находится
   автоматически из реестра Windows (`PassThruSupport.04.04`), причём это
   **не только Scanmatik**: любой корректно установленный J2534-драйвер
   попадёт в список. Например, на компьютере, где разрабатывалась
   программа, список находит сразу 10 устройств: Scanmatik SM2/SM3, NEXIQ
   USB-Link 2 (Bluetooth/USB/WIFI), Cummins USB-Link 3 (Bluetooth/USB/WIFI) и
   Kvaser. Кнопка 🔄 рядом со списком перечитывает реестр заново — пригодится,
   если адаптер подключили уже после запуска программы (сам список
   считывается один раз при старте).
2. Выбрать режим шины: **CAN** или **SAE J1939**.
3. Выбрать скорость (для CAN — 125000/250000/500000/1000000, для J1939 —
   250000/500000; поле редактируемое, можно вписать своё значение).
4. При желании поменять путь к файлу лога (по умолчанию —
   `logs\can_log_<дата_время>.csv`).
5. Нажать **СТАРТ**. Кадры пишутся в CSV непрерывно; в окне (если включён
   чекбокс "Показывать кадры в окне") — живой просмотр последних кадров.
6. **СТОП** — останавливает чтение, отключается от шины, закрывает файл лога.

### Формат CSV

```
pc_time_iso, pc_time_ms, device_ts_us, mode, baud, can_id_hex, extended_id, dlc, data_hex, rx_status_hex
```

- `pc_time_iso` / `pc_time_ms` — время на компьютере (полезно для сопоставления
  с другими логами).
- `device_ts_us` — таймстемп самого устройства J2534 (микросекунды от
  открытия устройства, не привязан к часам ПК).
- `can_id_hex` — CAN ID в hex (без префикса `0x`).
- `extended_id` — `1`, если 29-битный ID, иначе `0`.
- `data_hex` — байты данных через пробел, в hex.

## Диагностика проблем

- **"Не удалось загрузить ... (Win32 error 193)"** — DLL не 32-битная или мост
  собран не под win-x86. Проверьте, что `build_bridge.ps1` отработал без
  ошибок и что используется именно `bridge\publish\smbridge.exe`.
- **"PassThruOpen -> код ..."** — прибор не подключен/не виден Windows,
  занят другой программой (закройте фирменный софт Scanmatik, если он
  запущен), либо не тот путь к DLL.
- **"PassThruConnect -> код ..."** — устройство открылось, но не удалось
  подключиться на шину: неверная скорость, шина не запитана/нет терминаторов,
  либо (для J1939) неверный Protocol ID — см. раздел про J1939 выше.
- Кадров нет, но ошибок тоже нет — проверьте физическое подключение к CAN-шине
  и что на шине вообще что-то передаётся (зажигание/питание блока управления
  включено).

## Иденты и коды ошибок (DTC) — `can_dtc_reader_gui.py`

Отдельная программа поверх того же движка: разбирает диагностический обмен
**UDS (ISO 14229)** поверх CAN/J1939 и показывает:

- **Иденты** ЭБУ — номера ПО/железа, VIN и т.п. (`ReadDataByIdentifier`,
  сервис 0x22/0x62, DID из диапазона 0xF180-0xF19F по ISO 14229-1 Annex F);
- **Коды ошибок (DTC)** — сервис `ReadDTCInformation` (0x19/0x59): код вида
  `P0301`/`C101F`, статусные флаги (`pendingDTC`, `confirmedDTC` и т.п.),
  сырые байты;
- **События очистки DTC** — сервис `ClearDiagnosticInformation` (0x14/0x54).

Пять вкладок в окне программы:

1. **"Живое подключение"** — подключается к прибору через мост
   `smbridge.exe` и **сама активно опрашивает ЭБУ**: кнопки "Прочитать
   иденты" (запрашивает набор основных DID — VIN, номера ПО/железа и т.п.),
   "Прочитать DTC", "Очистить DTC" (с подтверждением — необратимо!) и
   отдельное поле для запроса произвольного DID. Таблица DTC здесь же
   показывает колонки "Активна" (testFailed, см. ниже) и "Тип
   неисправности" — расшифровку из `dtc_reference.py`.
2. **"Свои UDS-запросы"** — конструктор произвольного запроса поверх того
   же соединения (см. ниже).
3. **"Монитор шины"** — пассивный просмотр ВСЕГО трафика на шине (не
   только диагностического обмена) с записью в CSV и таблицей
   обнаруженных адресов блоков (см. ниже).
4. **"Ошибки всех блоков"** — опрос DTC сразу у всех адресов, видимых на
   шине, плюс их очистка (см. ниже).
5. **"Справочник Volvo"** — ручной поиск по расшифровке кодов ошибок из
   присланного Excel-файла (см. ниже).

Офлайн-разбор ранее записанного CSV-лога (без GUI) по-прежнему доступен из
командной строки: `py can_dtc_reader_gui.py --analyze лог.csv`.

   Адрес ЭБУ (DA) и адрес тестера (SA) — поля над кнопками, по умолчанию
   `23`/`F2` (как в реально захваченном логе). Если ЭБУ на другом адресе —
   поменяйте перед подключением.

   Адресация кадров (CAN ID для запроса/ответа) воспроизводит схему,
   реально увиденную в захваченном логе: верхний байт ID берётся **целиком**
   таким, каким он был в реальных кадрах (`0x1F`), а не собирается по битам
   Priority/EDP/DP из спецификации J1939 — на первой версии там была ошибка
   (не хватало бита EDP, из-за чего кадры уходили на несуществующий ID и ЭБУ
   их просто не видел; исправлено и проверено на реальной шине — см. ниже).
   Это НЕ стандартный J1939 Transport Protocol (PGN 0xEC/0xEB), а прямая
   адресация ISO-TP (Single/First/Consecutive/Flow-Control Frame прямо в
   8 байтах данных), которую использует ЭБУ в вашем логе. Многокадровые
   ответы ЭБУ (например, VIN) программа поддерживает — сама отправляет
   Flow Control кадр по приходу First Frame.

   **Проверено на реальной шине:** запрос VIN (0xF190) и чтение DTC получили
   настоящие ответы от ЭБУ (VIN собрался из First+Consecutive Frame в
   `YV2RG10A4HA810812`, полностью совпадает с тем, что было в исходном
   логе). Замечено, что ЭБУ иногда не отвечает на первую попытку (так же
   вело себя и в исходном логе — сторонний тестер там тоже слал повторы) —
   поэтому кнопки сами повторяют отправку до 4 раз, прежде чем показать
   "нет ответа".

   Если у другого ЭБУ адресация иная (например, честный J1939 TP или
   11-битный CAN ID) — активный опрос работать не будет, но офлайн-разбор
   ранее записанного лога (`--analyze`) не зависит от схемы адресации
   отправки и продолжит работать всегда.

### Вкладка "Свои UDS-запросы" — конструктор произвольного запроса

Позволяет отправить **любой** UDS-запрос, не только те, что зашиты в кнопки
вкладки "Живое подключение" — и при этом не заставляет вслепую набирать hex
целиком: сервис и параметры выбираются из списков с человекочитаемыми
именами (ReadDataByIdentifier, ReadDTCInformation, DiagnosticSessionControl,
ECUReset, SecurityAccess, WriteDataByIdentifier, TesterPresent,
RoutineControl), а рядом с каждым списком — hex-поле, куда можно вписать и
своё значение, если нужного варианта нет в списке. Например, для "чтения
идента" в выпадающем списке сразу видно "0xF190 — VIN", а не голое число.

Перед отправкой всегда видно строку **"Будет отправлено:"** с точными
байтами и их расшифровкой — так что понятно, что именно уйдёт на шину, ещё
до нажатия кнопки. Журнал внизу вкладки копит историю отправленных запросов
и ответов ЭБУ (или "нет ответа"/код ошибки, если ЭБУ не согласился) — его,
как и таблицы идентов/DTC, можно скопировать в буфер обмена (выделение +
Ctrl+C, правая кнопка мыши, либо кнопка "📋 Копировать").

Кнопка "➕ В очередь" добавляет собранный запрос в отдельный список ниже —
можно накопить несколько запросов, поменять порядок (▲/▼), убрать лишний, а
затем отправить их все подряд одной кнопкой "▶▶ ОТПРАВИТЬ ОЧЕРЕДЬ ПОДРЯД"
(с одним общим подтверждением, если среди них есть меняющие состояние ЭБУ).

Соединение — общее с вкладкой "Живое подключение" (адаптер Scanmatik отдаёт
эксклюзивный доступ только одному открывшему его процессу, поэтому второе
независимое подключение технически невозможно): сначала подключитесь там,
адреса ЭБУ/тестера тоже берутся оттуда.

Для сервисов, реально меняющих состояние ЭБУ (смена сессии, сброс, запись
идента, очистка DTC, запуск рутины, "свой запрос" произвольными байтами) —
перед отправкой запрашивается подтверждение, как и у кнопки "Очистить DTC".

**Многокадровые запросы.** Если payload длиннее 7 байт (например, длинное
значение для `WriteDataByIdentifier`, несколько DID в одном
`ReadDataByIdentifier` или своя длинная последовательность байт), программа
сама разбивает его на ISO-TP First Frame + Consecutive Frame(ы) и ждёт от
ЭБУ Flow Control между блоками (ISO 15765-2) — так же, как ЭБУ шлёт нам
Flow Control при получении её собственных многокадровых ОТВЕТОВ (например,
VIN), только в обратную сторону. Предел — 4095 байт (12-битное поле длины
классического ISO-TP), при превышении программа покажет понятную ошибку,
а не отправит обрезанные данные. Если ЭБУ не прислала Flow Control вовремя,
попытка отправки (не только ожидание ответа) тоже повторяется — до 4 раз,
как и остальные запросы.

**Проверено на реальной шине:**

- Однокадровые запросы через конструктор получили настоящие ответы ЭБУ —
  `ReadDataByIdentifier(VIN, 0xF190)` (тот же VIN `YV2RG10A4HA810812`),
  `TesterPresent` (`7E 00`), `ReadDTCInformation` с подфункцией
  `reportSupportedDTC` (0x19 0x0A, без маски статуса) — все три через
  реальные виджеты вкладки (выбор из списка → предпросмотр → отправка →
  журнал), не в обход GUI.
- Механика многокадровой ОТПРАВКИ (First Frame + Consecutive Frame) сама
  по себе проверена и корректно собирает/шлёт кадры (unit-тесты на сборку
  кадров + прямая проверка на шине). **Но** ЭБУ по адресу `0x23` в машине,
  на которой шла разработка, не ответила Flow Control ни на один
  многокадровый запрос (пробовали `ReadDataByIdentifier` сразу с 5 DID,
  11 байт payload) — на 6-секундное окно прослушивания шины после отправки
  First Frame не пришло вообще ничего, кроме обычного фонового трафика.
  Это значит, что конкретно эта ЭБУ, судя по всему, поддерживает приём
  только однокадровых диагностических запросов (что нередко для простых
  встраиваемых блоков — приём многокадровых запросов тестера, в отличие от
  отправки многокадровых ответов, часто не реализуется, если производителю
  это не требовалось). Функция при этом реализована правильно и будет
  работать с любой ЭБУ, которая отвечает Flow Control на First Frame —
  просто конкретно этот блок такие запросы не подтверждает.

### Вкладка "Монитор шины" — пассивный просмотр всего трафика

В отличие от двух других вкладок, ничего сама не запрашивает у ЭБУ — просто
показывает КАЖДЫЙ кадр, который видит адаптер на шине, независимо от того,
участвует он в диагностическом обмене или нет. Отдельного подключения не
требует и не открывает: использует то же самое соединение, что уже открыто
на вкладке "Живое подключение" (у J2534-адаптера только один эксклюзивный
канал), поэтому просмотр и подсчёт адресов идут **всегда**, пока то
соединение активно — заходить на вкладку специально не обязательно, она
копит данные в фоне.

Кнопка "● Начать запись"/"■ Стоп записи" включает и выключает только запись
в CSV поверх уже идущего мониторинга (путь к файлу — выше, есть "Обзор...").
Если соединение на вкладке "Живое подключение" разорвётся во время записи,
запись автоматически останавливается (файл корректно закрывается). Формат
CSV: `pc_time_iso, pc_time_ms, dev_ts_us, can_id_hex, extended_id, dlc,
data_hex, rx_status_hex, адрес, блок, pgn_hex`.

Ниже — отдельная таблица уникальных адресов блоков, обнаруженных на шине, с
попыткой расшифровать, что это за блок: для режима J1939 адрес — это байт
SA (источник) из 29-битного CAN ID, название — по стандартной таблице
**SAE J1939-71** (список Preferred Source Addresses, сверен по исходникам
протокольного анализатора Wireshark, `packet-j1939.c`); для обычного
CAN/OBD-II — по типовым диапазонам 11-битных ID (`0x7E0`-`0x7E7` запросы,
`0x7E8`-`0x7EF` ответы). Это ОРИЕНТИР, а не гарантия: конкретный
производитель мог отступить от стандартной таблицы адресов — например, наш
целевой ЭБУ на адресе `0x23` по стандартной таблице значится как "Hitch
Control" (управление сцепным устройством), что для тягача вполне
правдоподобно, но не 100% подтверждено документацией производителя.

Таблицу адресов, как и остальные таблицы в программе, можно скопировать в
буфер обмена (Ctrl+C / правая кнопка / кнопка "📋 Копировать таблицу").

**Фильтр по блокам.** Над таблицей адресов — два независимых переключателя:
"Фильтровать журнал (просмотр)" и "Фильтровать запись в CSV". Чтобы
отфильтровать трафик, сначала выделите один или несколько адресов в самой
таблице (Ctrl/Shift + клик — как обычно в списках Windows), затем включите
нужный переключатель. Переключатели независимы, поэтому можно, например,
смотреть на экране только один интересующий блок, а в CSV при этом писать
весь трафик целиком (или наоборот). Если ни одного адреса не выделено —
переключатель ничего не фильтрует, показывается/пишется весь трафик как
обычно (сделано намеренно: включённая галочка без выделения не должна молча
"съедать" все данные). Список адресов при этом продолжает пополняться
новыми блоками независимо от фильтра — отфильтрованные кадры просто не
попадают в журнал/CSV, но учитываются в таблице.

**Проверено:** headless-тест (`test_monitor_tab.py`) синтетическими кадрами
подтвердил корректный разбор SA (в т.ч. счётчик повторных кадров одного и
того же блока), запись в CSV с правильными полями, автоостановку записи при
разрыве соединения и копирование в буфер.

Запуск:

```powershell
py can_dtc_reader_gui.py
```

Есть и headless-режим (без окна, для проверки/скриптов) — печатает тот же
отчёт в консоль:

```powershell
py can_dtc_reader_gui.py --analyze logs\can_log_20260830_141405.csv
```

Проверено на реальном логе с полным сеансом диагностики (чтение VIN и
номеров ПО/железа, чтение и очистка DTC) — все значения расшифровываются
корректно.

### Вкладка "Ошибки всех блоков" — опрос DTC сразу у всех адресов на шине

В отличие от "Живого подключения" (там опрашивается только ОДИН адрес,
указанный в поле "Адрес ЭБУ"), эта вкладка сама находит все блоки, видимые
на шине, и опрашивает `ReadDTCInformation` (0x19, reportDTCByStatusMask) у
каждого по очереди.

Список блоков пополняется пассивно и автоматически — так же, как таблица
адресов на "Мониторе шины": вкладка подписана на поток "сырых" кадров
"Живого подключения" и запоминает каждый встреченный J1939 SA (с
расшифровкой по SAE J1939-71, где есть). Работает при любом активном
подключении, независимо от того, какая вкладка сейчас открыта. Адрес можно
добавить и вручную (поле "Добавить адрес вручную") — например, если блок
ещё ничего сам не передавал на шину, но его адрес известен из документации.

Кнопки:

- **"🔍 Опросить ВСЕ обнаруженные"** — опрашивает по очереди все адреса из
  таблицы.
- **"▶ Опросить выделенные"** — только выделенные строки (Ctrl/Shift + клик).
- **"⏹ Остановить"** — прерывает опрос между блоками (не разрывает обмен
  посередине одного запроса; общая для опроса и очистки DTC).
- **"🗑 Забыть все адреса"** — очищает таблицу (список начнёт наполняться
  заново по мере появления кадров на шине).
- **"🧹 Очистить DTC у выделенных"** / **"🧹 Очистить DTC у ВСЕХ
  обнаруженных"** — сервис `ClearDiagnosticInformation` (0x14), по очереди
  для каждого выбранного адреса, с обязательным подтверждением (необратимо!
  — то же предупреждение, что и у "Очистить DTC" на "Живом подключении", но
  сразу со списком всех затронутых адресов).

Технически опрос и очистка — это те же самые point-to-point UDS-запросы,
что и кнопки "Прочитать DTC"/"Очистить DTC" на "Живом подключении", просто
по очереди для каждого адреса: на время каждого запроса вкладка временно
переключает поле "Адрес ЭБУ" на нужный адрес (все операции в программе и
так идут по очереди через общую блокировку — одновременно с этим ничего
другого не отправляется) и возвращает его обратно, как только опрос/очистка
закончены или остановлены.

Результат опроса по каждому блоку — отдельная строка: "N DTC (M актив.):
●код1, ○код2, ..." / "ошибок нет" / "нет ответа (таймаут)" / "отрицательный
ответ: <NRC>", где ● — DTC активна ПРЯМО СЕЙЧАС (бит `testFailed`, 0x01
маски статуса, ISO 14229-1 Table D.1), ○ — неактивна (историческая, даже
если стоит `confirmedDTC`). Результат очистки — "DTC очищены" /
"очистка не выполнена: <NRC>" / "очистка: нет ответа (таймаут)". Полный
список кодов с флагами статуса, статусом активности и (предположительной)
расшифровкой типа неисправности — в журнале снизу.

**Проверено:** `test_all_dtc_tab.py` — headless-тест на синтетических
кадрах и фейковом обмене (без реального ЭБУ): обнаружение блоков и счётчик
кадров, ручное добавление адреса, опрос нескольких адресов подряд с верной
интерпретацией результата (DTC найдены / ошибок нет / таймаут /
отрицательный ответ), очистка DTC у выделенных адресов (успех и
отрицательный ответ), корректное восстановление поля "Адрес ЭБУ" после
опроса/очистки (в т.ч. после остановки на середине), отписка от кадров при
закрытии программы.

### Вкладка "Справочник Volvo" — расшифровка кодов ошибок

Построена на присланном пользователем файле `Коды_ошибок_RU.xlsx`
(загружается через `dtc_reference.py` из `dtc_reference_ru.json`, который
сгенерирован из этого Excel один раз). Две таблицы:

- **"Коды компонентов Volvo"** (5380 записей, `DiagnosticObjectId` вида
  `D1A0A` → русское название компонента/подсистемы) — только для РУЧНОГО
  поиска по ID или названию. Это внутренние последовательные ID Volvo,
  проверено (перебором base36), что они НЕ вычисляются из байтов DTC,
  реально приходящих с шины — нужна ещё отдельная таблица-связка конкретной
  прошивки ЭБУ с этими ID, которой в присланном файле нет. Поэтому эта
  таблица НЕ привязана автоматически к живым DTC на других вкладках.
- **"Типы неисправностей"** (164 записи, значение 3-го байта DTC-кода →
  русское описание) — расшифровывается **автоматически** на "Живом
  подключении" (колонка "Тип неисправности") и на "Ошибках всех блоков"
  (в журнале опроса). Судя по структуре справочника (все значения
  укладываются в один байт) и сопоставлению с реально прочитанными DTC, это
  похоже на прямую расшифровку 3-го байта, но это НЕ подтверждено
  официальной документацией Volvo — поэтому везде в интерфейсе помечено как
  предположительное.

Статус "Активна/Неактивна" (бит `testFailed`), в отличие от типов
неисправности, — это стандартный бит статуса DTC по ISO 14229-1, не
зависит от справочника Volvo и не является предположением.

### Потеря кадров и повреждение многокадровых обменов при плотном трафике

При реальной эксплуатации на плотной шине была замечена деградация: доля
"повреждённых" многокадровых (First+Consecutive Frame) UDS-обменов росла от
файла к файлу. Разбор занял два раунда и вскрыл сразу несколько отдельных
проблем — по отдельности каждая маскировала другую:

1. **Грубое разрешение временных меток (~15 мс).** `smbridge.exe` брал
   `DateTime.UtcNow` на каждый кадр — у Windows это по умолчанию тикает
   примерно раз в 15 мс, из-за чего несколько по-настоящему разных кадров,
   пришедших близко друг к другу, получали ОДИНАКОВЫЙ `pc_ms` и в логе
   выглядели как дубликаты запроса. Исправлено: точка отсчёта берётся один
   раз при старте моста, дальше время считается через `Stopwatch`
   (`ElapsedMilliseconds`) — разрешение много точнее.

2. **`IsoTpReassembler` молча склеивал кадры при разрыве последовательности.**
   Если терялся один Consecutive Frame, сборщик всё равно принимал
   следующий пришедший CF, не проверяя номер последовательности — на выходе
   получалось "целое на вид", но на самом деле повреждённое UDS-сообщение,
   без какого-либо сигнала об ошибке. Исправлено: `IsoTpReassembler` теперь
   ведёт счётчики `started`/`completed_ok`/`corrupted_gap`/`abandoned` и при
   разрыве последовательности НЕ отдаёт наружу поддельно-"собранные" байты
   (`feed()` возвращает `None`, буфер сбрасывается). Статистика видна и в
   живом режиме (строка "Повреждено многокадровых: N/M" рядом со счётчиком
   кадров на вкладке "Живое подключение"), и в офлайн-отчёте (`--analyze` /
   `format_report()`) — там же показан процент повреждения.

3. **`dtc_report.analyze_csv_file` читал колонки CSV по фиксированной
   позиции.** У вкладки "Монитор шины" и у `can_logger_gui.py` разный набор
   и порядок колонок — при чтении по номеру колонки один из форматов
   читался с "чужими" значениями в чужих полях (например, `dlc` вместо
   `can_id_hex`), что само по себе выглядело как повреждение данных, даже
   когда реальной потери кадров не было. Исправлено: колонки теперь ищутся
   по имени (`csv.DictReader`), одна и та же функция корректно работает с
   обоими форматами.

4. **Настоящая причина потери кадров: блокирующая запись в stdout моста.**
   `smbridge.exe` писал каждый принятый кадр в stdout синхронно (с явным
   `Console.Out.Flush()`) в том же потоке, что вызывал
   `PassThruReadMsgs` — если труба к Python-процессу на миг подвисала,
   `Flush()` блокировал этот поток, чтение с шины останавливалось, и пока
   мост не мог позвать `PassThruReadMsgs` снова, собственный внутренний
   буфер J2534-драйвера переполнялся и молча терял кадры. Именно это чаще
   всего рвёт Consecutive Frame посередине многокадрового обмена.
   Исправлено: чтение с шины и запись в stdout разделены — `ReaderLoop`
   кладёт готовые строки в `BlockingCollection<string>` (очередь на 50000
   кадров), а отдельный поток-писатель разбирает эту очередь и пишет в
   stdout уже без риска застопорить чтение.

**Статус проверки:** пункты 1-3 проверены офлайн-тестами
(`test_reassembly_fix.py`, без реального прибора) и живым чтением идентов
на реальной шине. Пункт 4 (мост) успешно собран (`dotnet publish`,
`bridge\publish\smbridge.exe` пересобран и разложен) и запускался на
реальном приборе без ошибок, но получить численное подтверждение
("процент повреждения снизился с X% до Y%") на живом плотном трафике пока
не удалось: во время попыток проверки (`test_bridge_throughput_fix.py`,
несколько раундов чтения идентов подряд в течение ~7 минут) на шине не
оказалось ни одного кадра — судя по всему, автомобиль/ЭБУ на момент теста
не был запитан. Диагноз при этом сделан не "на глаз", а по факту: причина
(блокирующий `Flush()` в общем потоке с `PassThruReadMsgs`) видна прямо в
исходном коде, и статистика `corrupted_gap`/`abandoned` из уже
записанных логов пользователя (`monitor_20260904_182544.csv`: 26/43 = 60%,
`monitor_20260904_191752.csv`: 20/44 = 45%) подтверждает, что повреждение
было реальным, а не артефактом старого бага в `analyze_csv_file`. Чтобы
получить финальное численное подтверждение эффекта фикса, нужно повторить
запись через "Монитор шины" при реально работающем двигателе/зажигании и
плотном трафике на шине, затем сравнить процент через `--analyze`.

### Формат кода DTC

Три байта DTC от ЭБУ (`b0 b1 b2` + байт статуса) раскладываются в привычный
код по классической схеме SAE J2012/ISO15031-6 (`b0`/`b1` → напр. `C101F`);
третий байт (`b2`) показывается отдельно как "сырой" — его трактовка
зависит от конкретного производителя ЭБУ и в классическую 5-символьную
схему не входит. Для Volvo `b2`, предположительно, дополнительно
расшифровывается в текст через `dtc_reference.py` (см. вкладку "Справочник
Volvo" выше).
